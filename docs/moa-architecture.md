# MoA+：目标、角色与协作方式

MoA+ 的目标是通过 Agent 之间的协作，把系统的智能能力推向下一个台阶。它把多个独立的执行上下文、共享知识、可中断通信与结果审阅组织成一支可以持续工作的团队。Coordinator 对全局方向和交付负责，Workers 在各自的上下文中推进具体责任，已经确认的知识继续服务后续任务。

MoA+ 以 DeepSeek Harness 插件的形式，复用原生运行体、会话、工具、收件箱、权限和后台任务。这份文档说明 Coordinator 与 Workers 的职责、生命周期和协作流程；模块与数据模型见[代码架构](architecture.md)，工具行为见[工具 API](tool-api.md)，运行环境要求见[兼容说明](compatibility.md)。

## 为什么需要协作

复杂长程任务会遇到三类结构性问题：

- **上下文腐烂。** 工具输出和反复试错持续膨胀主会话，使最初的约束逐渐失焦。Worker 承接执行细节，Coordinator 保持全局记录，Context 保存可复用知识。
- **思维框架自锁。** 沿着既定方向自我审查，容易重复同一套假设。独立 Task 从干净上下文出发，Fork 继承确实需要的记忆，独立审阅回到原始要求与实际产物。
- **串行瓶颈与信息孤岛。** 单 Agent 逐项推进限制吞吐；简单增加 Agent 又容易重复搬运背景或覆盖文件。隔离 worktree 支持并行尝试，直接通信交换问题和发现，索引式知识让后续工作继续受益。

这些机制可以组合成探索、执行、比较、审阅、返工和继续的工作流程。运行时负责把消息送达、释放等待和保留执行状态，Agent 根据任务判断如何合作；模型判断和实际任务结果共同决定团队的表现。

## 同构运行体，不同权责

Coordinator 与 Worker 使用同一套原生 Agent Loop。区别在于身份、工具和继承权限。身份写入对话历史：Task 放在初始任务之前，Fork 放在继承历史之后，说明实际 ID、目录与隔离方式、`reportTo` 和汇报要求，不为每个 Worker 改写 System Prompt。

Coordinator 直接面对用户，负责目标、任务拆解、方向判断、结果综合和最终交付。它保留普通执行工具，也可以做澄清、协调、综合和简单完整的操作；分工按整个责任判断，不靠任务关键词或命令次数硬性规定。

Worker 对一个明确的执行或调查责任持续工作，可以是只读 Explorer、Planner、联网 Deep Research 或通用执行者。Explorer 和 Planner 只有文件探查工具，没有 Bash；需要运行命令、构建或测试的责任应选择 General-purpose，即使只是只读验收。Coordinator 明确各条工作线的责任人，传递已有结论与产物，复用已完成的检查，独立审阅则聚焦尚未解决的问题或风险。默认不开放下级派生；需要多层团队时明确启用 `nested`。创建者、Fork 的历史来源和最终汇报对象是三个不同的事实。

## Coordinator 的操作流

1. 收到新用户消息，先用 `QueryAgent` 看当前 Workers；用户可能直接修改过子会话，不能只依赖旧分工。需要细节时读取明确下标和长度的人类／AI 历史窗口。
2. 读取工作记录和上下文索引，判断延续已有 Worker、用 `Task` 冷启动，还是用 `Fork` 继承某个成员的有效记忆。给出完整目标、约束、上下文引用和预期产物。
3. 更新 `notes.md` 的分工、进度和阻塞。默认隔离工作区；需要在父目录共同落盘时显式使用 `shared`。原生容量上限与 Task 单次最多 20 个是两项不同约束。
4. 用 `SendMessage` 引导工作：`steer` 在下个安全步骤接入，`queue` 留到后续 turn。Notify 接受后返回；Request 在当前工具调用中等待，回答必须带明确的 `reply_to`。
5. 需要等待时使用可被来信、完成、超时或 Stop 中断的 `QueryAgent`。需要立刻改方向时，用 `KillAgent` 等待旧执行实际退出，再发送新指令；停止待命与显式销毁分开处理。
6. 每轮真正结束的 Worker 自动把完整最后一条 AI 消息交给 `reportTo`，默认是创建者。空结果也会回传；Coordinator 可查历史、继续下发或改变分工。转后台交接不是完成。
7. 审阅证据和产物，补齐具体缺口，整理知识与工作记录。相关工作和结果处理完毕后再交付；过程中保持对用户输入的响应。

这些操作让 Coordinator 承担原本由人完成的上下文管理和协调判断。它不只是把一个大 Prompt 分给几次一次性调用。

## Worker 的工作方式

Worker 先读共享索引，按需获取当前责任所需的上下文。遇到阻塞时先利用已有知识；需要上级判断则 Request 提问，等待原生 Tool Result，不凭空假设答案。Notify 用于无需阻塞的进度和同伴信息，普通通知不要求反复回复“收到”。

结束时给出自包含的 AI 消息：做了什么、结果与证据、文件或产物、补充了哪些可复用知识，以及未解决事项。系统自动回传完整正文，不需要再手工发送一份重复结果。用户也可以直接操作该会话，新的指令继续遵循原生 steer／queue 和权限。

## 五态与工作区

| 状态 | 含义 |
| --- | --- |
| Idle | 已创建，还未开始一轮工作。 |
| Running | 正在执行；Request 在 Tool Call 内等回答也属于 Running。 |
| Waiting | Query 等待协作进展或原生人工确认。 |
| Aborting | 已请求取消，实际协程或资源仍在清理。 |
| Zombie | 当前工作结束／停止后保留会话与工作区，SendMessage 可以继续。 |

这是原生活动、等待和清理事实的派生视图，不是另一套调度状态机。冷会话也不等于无法使用；恢复按真实父子链进行，不用假消息唤醒中间父会话。

Isolated 默认使用独立 Git worktree，带入源目录当前的暂存、未暂存和未跟踪内容。Shared 直接操作创建者的目录。普通结束或 Kill 保留目录；显式销毁才清理拥有归属标记的隔离资源，不删除共享源目录。

## 工作记录与共享知识

```text
workspace/
├── notes.md                 Coordinator：阶段、待办、分工、进度、阻塞、产物引用
├── archived.md              Coordinator：告一段落的工作及结果
├── rubrics.md               独立验收标准
└── context/
    ├── index.md             共同维护：文件路径与简短介绍
    └── ...                  可复用的事实、决策和方法
```

`notes.md` 由 Coordinator 维护，Host 在它每次推理前完整注入。超过 8,000 字符只追加整理提醒，不截断；Coordinator 把已完成条目及结果移入 `archived.md`，把有复用价值的详细背景移入 Context。

Coordinator 与 Workers 共同维护 Context。Agent 先读索引，再按需读正文；派活传文件引用，不反复复制大段背景。Worker 在符合当前任务写入要求时贡献确认过、可复用的新发现；任务内推导和例行检查清单留在指定产物或最终结果，没有新知识时无需更新 Context。Coordinator 更多负责合并、整理和删除过时内容。`ProjectContext` 从隔离 worktree 访问真正的共享库，按版本替换避免覆盖别人刚写的内容。进度留在工作记录，知识留在 Context。

已有保存路径继续保留，旧 `context/context.md` 文件也不会被覆盖。相同 cwd 的会话共享这些工作区文件；独立项目宜使用独立工作区。

## 后台工具与完成门禁

慢工具超过阈值后，可按 AfterSeconds、NewMessage 或轻量 LLM Judge 策略转后台。没有新消息的 AfterSeconds 在当前 turn 内继续思考；消息驱动的转后台写入 Tool Message 占位、结束原 turn，再由新消息开启下一轮。真实结果随后回流，Agent 可以查询、取消，并在空闲时被唤醒。

`set_completion_criteria` 可以绑定任务完成标准和完整承诺原文，Ralph 在结束出口检查。Coordinator 还有独立出卷和判卷：Builder 只看原始人类需求与规格快照，使用模型支持的最低推理档位提取标准；Verifier 读 `rubrics.md` 并通过原生工具检查产物，保留用户选择的推理设置。未通过、缺证据或不完整的承诺会触发继续工作。内部催办消息不变成新的原始需求，避免验收标准被实现过程污染。

Verifier 通过私有的 `submit_verdict` 工具提交本次判词，直接结束原生审查轮次。提交不算取证，也不能代替必需的成功测试；旧的合法 JSON 判词格式继续兼容。判词与当前候选绑定，中断或下一次审查不会复用旧的 Pass。Coordinator 会收到与实际配置一致的自动验收说明，知道 `rubrics.md` 由宿主管理、最终验收如何运行；关闭配置时则明确说明未启用，不给 Worker 注入这项 Coordinator 专属保证。

原生循环仍负责并行工具的前台屏障、取消后结果配对和结束前收件箱检查。详细的结构体、函数及原生边界见[代码架构](architecture.md)与[工具 API](tool-api.md)。
